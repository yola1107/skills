# Go Code Simplifier

在保持行为不变的前提下，提高 Go 代码的清晰度、一致性和可维护性。取舍顺序是：**行为等价 > 清晰 > 简单 > 短**。这里的清理就是 Fowler 意义上的 refactoring：每个改动都要能说出等价理由。

## 风格依据

项目规则优先，包括 AGENTS.md、CLAUDE.md 和 lint 配置；项目没有约定的地方，以 [Effective Go](https://go.dev/doc/effective_go)、[Go Code Review Comments](https://go.dev/wiki/CodeReviewComments) 和 [Go Doc Comments](https://go.dev/doc/comment) 为准。新语法和新的标准库 API 按 `go.mod` 声明的 Go 版本判断能否使用。排版交给 `gofmt`，标准库 import 放在第一组。

## 清晰度

- **控制流**：先处理错误和边界，用提前 return 或 continue 退出，让主流程不缩进；分支以 return、break 或 continue 结束时，去掉后面的 else。只在单个分支内使用的值，放进 if 或 switch 的初始化语句；其他声明靠近首次使用的位置。
- **命名**：采用 MixedCaps，缩写词大小写保持一致（`ID`、`URL`）。名字长短与作用域、使用距离相称，`i`、`err`、`ctx` 这类惯用短名保留。按业务角色命名，同一概念用同一个叫法，不重复包名、类型名等上下文已经表达的信息。receiver 名同一类型内保持一致，项目统一写法（例如 `this`）优先于静态检查的告警。
- **返回**：删除只为转抄结果而存在的中间变量、多余判断和重复类型。命名结果只在解释返回契约或者 defer/recover 需要时保留；短函数可以用裸 return，较长的函数写显式 return。
- **冗余**：删除被注释掉的代码、未使用的声明，以及算完不用的计算。
- **注释**：删除复述代码的注释，修正与代码矛盾的注释；保留解释原因、契约、工具指令和阶段分隔的注释。新写或修正 doc comment 时，按 Go Doc Comments 的写法，用以被声明名字开头的完整句子，中文注释也一样，例如 `// Bet 处理玩家下注。`；内容正确的现有注释，不为格式单独改写。注释只描述代码当前做什么；疑似缺陷写进报告。

## 适度

- 保留能帮助理解或调试的中间变量和抽象。有清晰的 if/else 或 switch，就不写嵌套表达式和过于紧凑的一行式。
- 只有输入、失败路径、执行顺序和职责都一致时，才合并重复逻辑。提取函数要让调用处一眼看得出流程和失败出口。
- 改动以阅读收益为准，已经清楚的代码零修改。整包统一风格的机械改写（例如命名返回值全部改成显式 return），只在能顺带收窄作用域或消除歧义时才做。

## 可观察行为

改动前后以下内容保持一致：

- 返回值、错误身份与文本、失败路径的部分返回值、panic。
- 对外调用（RPC、数据库、消息推送、定时任务）的参数、次数和顺序。
- 日志的级别、文本和字段，包括写错的格式串。
- 锁的对象、临界区范围和加锁顺序；goroutine、defer 和资源的生命周期。
- 导出标识符、接口签名，以及通过反射、字符串注册或配置引用的名字（路由、RPC 方法名、表名）。
- 求值次数与顺序、短路、nil 与空集合、切片共享与容量。

## 改动分类

每个候选归入三类之一：

- **等价改动**：给得出等价理由就直接实施。理由有三种：
  - 编译器保证：例如删除未使用的声明。
  - 局部改写：例如控制流、作用域、返回值的改写，前提是返回值、短路和执行顺序都不变；也包括对未导出符号改名，前提是已经查清所有引用。
  - 已核实：删除调用或计算前，读过被调函数的实现，确认没有副作用。
- **待决改动**：有收益，但需要人判断，只列出不实施。包括：
  - 改动导出名，或通过反射、字符串引用的名字；
  - 删除薄包装、提取跨职责的函数；
  - 改动临界区内执行的代码；
  - 依赖运行时不变量的改写（例如假设两个 id 总是相等）；
  - 看起来多余、但可能有作用的代码，按 Chesterton's fence 处理（例如空的加锁/解锁对）。
- **发现**：缺陷、竞态、安全问题、日志格式错误。代码保持原样，写进报告。

## 流程

1. **范围与基线**
   - 未指定范围时处理当前改动；指定文件或目录时，覆盖其中全部手写 Go 代码和测试，跳过 vendor 和生成代码。
   - 检查 `git status`。工作区有用户改动时，以包含这些改动的状态为基线，并保留这些改动。
   - 从仓库里找验证入口：Makefile、CI 配置、lint 配置、AGENTS.md、CLAUDE.md。
   - 运行并记录以下检查：目标包及其调用方所在包的 `go build`，以及 `go vet` 和 `go test`。连接外部网络或数据库的测试跳过。仓库配置了 staticcheck 或 golangci-lint 的，一并记录结果。缺少的工具只记录，不安装。
   - 完成标准：每条验证命令的基线结果都已记录，已有的失败标为既有失败。

2. **通读与分类**
   - 按文件读完整函数，弄清每条路径的返回值、副作用、锁和调用顺序。
   - 改名、删除或改签名之前，先查清所有引用：有 gopls 就用 gopls，否则用 `rg -w` 或 `grep -rw` 搜标识符，再搜它的字符串形式。
   - 完成标准：范围内每个文件都已读完，每个候选都已归入三类之一。

3. **分批实施等价改动**：按“清晰度”一节的条目分五批，顺序为冗余（含静态检查指出的多余写法）、控制流、返回、命名、注释。改名时同步更新所有引用。

   每批完成后重跑第 1 步的全部命令，结果与基线一致才进入下一批。用户允许提交时，一批一个提交；否则在报告中按批列出文件和改动。改写纯函数的内部逻辑前，先补 characterization test 固定现有输出，测试随改动一起保留。
   - 完成标准：每批都通过验证，并且 `git diff -w` 里只有该批类型的改动。

4. **复核**
   - 逐批阅读 diff，确认每处改动都有阅读收益，并重新说一遍它的等价理由；说不出的撤回，归入待决。
   - 结构改动可能带出新的清理机会，只在受影响的函数内处理。
   - 完成标准：每处改动都有收益和等价理由。

5. **报告**：按下方模板交付。

## 验证陷阱

- Windows 的 CRLF 工作区里，`gofmt -l` 会把每个文件都报出来。先把文件转成 LF 副本放到临时目录，再在那里检查。
- 删除声明块中的某一行（包括注释行），可能让上下两段对齐区域合并，导致 gofmt 重排整块。必要时在原位置保留一个空行。
- 只打印、不断言的测试不能证明等价。
- 涉及并发的改动跑 `go test -race`，它依赖 cgo；跑不了的话，在报告中注明。

## 报告模板

```markdown
## 结果
<范围、批次数、最终验证结论>

## 已实施（按批）
1. <批次>：<文件> — <改动>；等价理由：<编译器保证／局部改写／已核实 …>

## 待决
- `<文件:行>` <建议改动> — <需要判断的原因>

## 发现（未修改）
- `<文件:行>` <现象> — <影响>

## 验证
- <命令>：基线 <结果> → 结束 <结果>
- 跳过：<检查> — <原因>
```
