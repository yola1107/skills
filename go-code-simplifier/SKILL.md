# Go Code Simplifier

在指定范围内降低 Go 代码的理解负担，保持现有行为。取舍顺序：**行为等价 > 清晰 > 显式 > 简单 > 短**。每处改动都要有可说明的阅读收益和等价理由；已经清楚的代码保持原样。

以项目规则（AGENTS.md、CLAUDE.md、lint 与 goimports 配置）为准，未规定的部分参考 [Effective Go](https://go.dev/doc/effective_go)、[Go Code Review Comments](https://go.dev/wiki/CodeReviewComments) 和 [Go Doc Comments](https://go.dev/doc/comment)。新语法、标准库 API 和循环变量语义，以文件实际生效的 Go 版本为准；排版交给 `gofmt`。

## 写法

优先处理死代码、复杂控制流、重复处理流程、过大作用域和职责不清的命名，让读者少追踪分支、少记住状态、少重复理解同一段逻辑。行数不是收益标准。

下面的写法用于解决具体阅读问题，不作为遍历整包统一风格的清单。项目强制或用户明确要求统一风格时遵循；否则，`this` 改名、裸 return 改写、`any` 替换和 import 调整都要有局部阅读收益。

- **冗余**：删除已证明无用的声明、计算、分支和注释掉的代码；仅当输入、失败路径、执行顺序和职责都相同时，合并重复处理流程。
- **控制流**：先处理错误与边界，减少嵌套。对输入、输出和职责清楚的一段逻辑，可提取能说明业务步骤的小函数，保持调用位置、执行顺序和资源生命周期；长函数本身不是拆分理由。
- **作用域**：让变量靠近实际使用位置，减少贯穿整个函数的临时状态；适合时放入 if/switch 初始化语句。
- **显式**：用明确的返回表达式、字段名和必要的类型信息帮助理解；保留能给步骤命名、便于调试的中间变量和小函数，保持调用嵌套浅、一行一件事。
- **命名**：修正误导或职责不清的名字，采用 MixedCaps、`ID`/`URL` 等惯用缩写；名字长短与作用域相称，保留 `i`、`err`、`ctx` 等惯用短名，同类型 receiver 保持一致。
- **现代写法**：仅在更易读且语义相同时采用 `any`（1.18+）、`slices`/`maps`（1.21+）、整数 range 或省去循环变量副本（1.22+）。
- **import**：遵循项目配置；没有规定时按标准库、本项目包（module 路径前缀）、第三方包分组，组间空一行，只在名字冲突时使用别名。
- **注释**：删除复述代码的说明，修正与代码矛盾的文字，保留原因、契约、工具指令和阶段分隔。新写或修正的 doc comment 以声明名开头，写成完整句子，补充签名未表达的信息；只描述有依据的当前行为。

## 可观察行为

改动前后，以下内容保持一致：

- 返回值、错误身份与文本、失败路径的部分返回值、panic。
- 对外调用（RPC、数据库、消息推送、定时任务）的参数、次数和顺序。
- 日志的级别、文本和字段，包括写错的格式串。
- 锁的对象、临界区范围和加锁顺序；goroutine、defer 和资源的生命周期。
- 导出标识符、接口签名、导出的 struct 字段名与 tag，以及通过反射、字符串注册或配置引用的名字（路由、RPC 方法名、表名）。
- 求值次数与顺序、短路、nil 与空集合、切片的共享与容量、浮点舍入。

## 改动分类

- **等价改动**：满足参考前提，并能说明行为不变：由编译器保证，或已查清所有引用且局部返回值、短路与执行顺序不变，或已核实相关实现没有副作用。
- **待决改动**：有收益，但需要人来判断，只列出、不实施。包括：改名或删除导出标识符（仓库外可能有引用），改动导出字段或带 tag 的字段名、错误文本，或通过反射、字符串引用的名字；删除薄包装，或提取跨职责的函数；改动临界区内执行的代码；依赖运行时不变量的改写（例如假设两个 id 总是相等）；看起来多余、但可能有作用的代码，按 Chesterton's fence 处理（例如空的加锁/解锁对）；前提无法确认的改写。
- **发现**：缺陷、竞态、安全问题、被丢弃的 error、日志格式错误、看起来本意是给外层变量赋值的 `:=` 遮蔽、注释可能才是本意而代码写错的地方。代码保持原样，写进报告。

## 流程

改动留在工作区，由用户审阅 diff 后自行提交；不暂存、不提交、不推送。集中读取和搜索，复用仍有效的代码理解、引用关系、配置与工具检查结果；追加检查用于解决具体疑问。

1. **确定范围，先分析**
   - 未指定范围时处理当前改动，没有改动就询问范围；指定文件或目录时，读完其中全部手写 Go 代码和测试，跳过 vendor 和生成代码。
   - 查看 `git status`，保留用户已有改动并记下文件；从项目规则、Makefile、CI 和 lint 配置找到验证入口。
   - 按完整函数理解各路径的返回值、副作用、锁与调用顺序，选出有阅读收益的候选。只记录非显然的改动与等价依据、待查证项、待决和发现；简单已证等价项不要求逐项表格。
   - 执行候选前，读取并满足 [Go 等价改写前提](references/go-equivalence-pitfalls.md) 的对应章节：「冗余」「控制流」「作用域」「显式」「命名」「现代写法」「import」与上述候选同名；测试、格式处理查「验证」。参考文件较短，可以一次读完后复用。
   - 集中查清相关符号的引用和被调实现；有 gopls 时优先查语义引用，字符串、tag 和其他构建标签等按参考文件补查。范围分析完成后，确定可实施改动及受影响包、调用方；没有可实施项就报告零改动。
2. **整体实施，按需验证**
   - 有代码修改时，默认在任何修改前运行一次相关范围的基线，在最终状态运行一次完整验证。沿用仓库入口，覆盖受影响包及调用方的构建、静态检查和测试（通常为 `go build`、`go vet`、`go test`）；仓库要求的其他检查照常执行。缺少工具只记录、不安装，跳过需要连接外部网络或数据库的测试并说明原因。
   - 改动涉及分支、边界值或集合语义时，检查相关测试的输入与断言。确有缺口时，在改写前的实现上补并运行 characterization test，固定现有输出或副作用，保留测试及结果作为比较依据；改名、注释、格式调整不补测试。
   - 覆盖率只辅助定位未执行的语句，不能代替分支、边界、nil 和执行顺序的语义断言；仅在需要时读取已有 profile，或用 `go test -coverprofile` 和 `go tool cover -func` 生成、查看。
   - 按相互依赖的实际改动整体实施，格式化改动文件。中间仅在具体语义风险、测试断言缺口或失败定位需要时追加相关检查；类别和补丁数量不决定验证次数。
3. **复核并报告**
   - 通读完整 diff，每处改动都应有阅读收益和等价理由；说不清的撤回、列为待决。新机会仅在受影响函数内处理。
   - 最终验证与基线比较：构建和静态检查没有新增失败或诊断；测试结果逐条一致，既有失败变为通过也需查明。失败时围绕差异定位，修正或撤回相关改动。已有验证仍覆盖最终状态时直接复用。
   - 报告有收益的改动、全部待决与发现、实际验证结果（基线 → 结束、未运行检查及原因），注明用户原有改动；零改动时明确说明，未运行检查不能表述为通过。
