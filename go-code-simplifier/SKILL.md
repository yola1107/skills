# Go Code Simplifier

按 Go 官方风格清理 Go 代码，目标是读起来更直接、写法更显式、冗余更少，同时外部行为保持不变。取舍顺序是：**行为等价 > 清晰 > 显式 > 简单 > 短**。这里的清理就是 Fowler 意义上的 refactoring，每处改动都要说得出等价理由。

## 风格依据

以 [Effective Go](https://go.dev/doc/effective_go)、[Go Code Review Comments](https://go.dev/wiki/CodeReviewComments) 和 [Go Doc Comments](https://go.dev/doc/comment) 为准，辅以 `go vet` 与 Go 团队的 [modernize](https://pkg.go.dev/golang.org/x/tools/go/analysis/passes/modernize) 分析器。下面的写法是默认做法；项目规则（AGENTS.md、CLAUDE.md、lint 与 goimports 配置）可以补充或覆盖。新语法、标准库 API 和循环变量语义，以文件实际生效的 Go 版本为准。排版交给 `gofmt`。

## 写法

分析时逐个函数对照以下检查清单，防止漏项；实施顺序见流程第 4 步。每类改写的等价前提和反例集中在参考文件中，第 2 步读取。

- **冗余**：删除被注释掉的代码、未使用的声明、计算后不再使用的结果，以及多余的 `break`、`return`。
- **控制流**：先处理错误和边界，用提前 return/continue 退出；分支以 return、break 或 continue 结束时，去掉后面的 else；对同一个变量反复比较时改用 `switch`。
- **作用域**：只在单个分支内用到的值，放进 if/switch 的初始化语句。
- **显式**：return 时写出返回值，不用裸 return；命名结果只用于区分同类型的多个返回值，或供 defer/recover 读写；复合字面量写字段名；去掉函数体内的 `_ = x` 占位赋值；删除冗余的类型转换。
- **命名**：MixedCaps，缩写词整体大写或整体小写（`ID`、`URL`）；名字长短与作用域相称，保留 `i`、`err`、`ctx` 这类惯用短名；不重复包名已表达的信息；receiver 用类型名的 1–2 个字母缩写，同一类型的所有方法保持一致，不用 `this`/`self`。
- **现代写法**：`interface{}` 改为 `any`（1.18+）；手写的查找、排序循环在语义完全相同时改用 `slices`/`maps`（1.21+）；计数循环改为 `for i := range n`（1.22+）；删除循环变量拷贝 `v := v`（1.22+）。
- **import**：对本次改动到的文件，按标准库、本项目包（以 `go.mod` 的 module 路径为前缀）、第三方包分三组，组间空一行；只在名字冲突时使用别名。
- **注释**：删除复述代码的注释，修正与代码矛盾的注释，保留解释原因、契约、工具指令和阶段分隔的注释；新写或修正的 doc comment 以被声明的名字开头，写成完整的句子，内容超出签名已表达的信息，例如 `// Save 校验配置后写入磁盘，并通知订阅者。`；注释只描述代码当前的行为，不补写没有依据的意图。

## 适度

- 一个有意义的中间变量或小函数，能给某个步骤起名字，便于阅读和调试，应当保留。
- 行数服从可读性：一行只做一件事，调用嵌套保持浅，职责不同的逻辑分开写。
- 只有输入、失败路径、执行顺序和职责都相同时，才合并重复的逻辑。
- 已经清楚的代码保持原样。

## 可观察行为

改动前后，以下内容保持一致：

- 返回值、错误身份与文本、失败路径的部分返回值、panic。
- 对外调用（RPC、数据库、消息推送、定时任务）的参数、次数和顺序。
- 日志的级别、文本和字段，包括写错的格式串。
- 锁的对象、临界区范围和加锁顺序；goroutine、defer 和资源的生命周期。
- 导出标识符、接口签名、导出的 struct 字段名与 tag，以及通过反射、字符串注册或配置引用的名字（路由、RPC 方法名、表名）。
- 求值次数与顺序、短路、nil 与空集合、切片的共享与容量、浮点舍入。

## 改动分类

每个候选改动归入以下三类之一：

- **等价改动**：满足参考文件中的前提，并给得出以下理由之一，就直接实施：
  - 编译器保证；
  - 局部改写：返回值、短路和执行顺序不变，所有引用都已查清；
  - 已核实：读过相关实现，确认没有副作用。
- **待决改动**：有收益，但需要人来判断，只列出、不实施。包括：改名或删除导出标识符（仓库外可能有引用），改动导出字段或带 tag 的字段名、错误文本，或通过反射、字符串引用的名字；删除薄包装，或提取跨职责的函数；改动临界区内执行的代码；依赖运行时不变量的改写（例如假设两个 id 总是相等）；看起来多余、但可能有作用的代码，按 Chesterton's fence 处理（例如空的加锁/解锁对）；前提无法确认的改写。
- **发现**：缺陷、竞态、安全问题、被丢弃的 error、日志格式错误、看起来本意是给外层变量赋值的 `:=` 遮蔽、注释可能才是本意而代码写错的地方。代码保持原样，写进报告。

## 流程

改动留在工作区，由用户审阅 diff 后自行提交；skill 不暂存、不提交，也不推送。

工具调用服务于具体问题：文件读取和同批符号的搜索集中进行；已读的内容和已确认的引用关系，没有相关改动时直接复用；只有新疑问、修改或失败才触发新的读取和检查；验证失败时围绕失败定位，不重新扫描整个范围。

1. **范围**
   - 未指定范围时，处理当前的改动，没有改动就询问范围；指定了文件或目录时，覆盖其中全部手写的 Go 代码和测试，跳过 vendor 和生成的代码。
   - 查看 `git status`；工作区已有用户改动时，保留这些改动，并在报告里列出这些文件。
   - 从 Makefile、CI 配置、lint 配置、AGENTS.md、CLAUDE.md 找验证入口。
   - 完成标准：文件清单和验证入口都已确定。
2. **分析与清单**
   - 读完参考文件 [references/go-equivalence-pitfalls.md](references/go-equivalence-pitfalls.md)。
   - 按文件读完整的函数，弄清每条路径的返回值、副作用、锁和调用顺序，并对照「写法」检查清单找出候选。
   - 每个候选记录一行：位置／函数 → 当前问题 → 拟修改方式 → 等价依据 → 待查证事项。同一位置的多类改写、相互依赖的改写合并为一项。
   - 集中查证待查证事项：查清同批符号的引用（有 gopls 就用 gopls，否则用 `rg -w`、`grep -rw` 或 PowerShell 的 `Select-String`，再按参考文件补查其他形式的引用），读取相关被调函数的实现。
   - 根据可实施清单确定受影响包、调用方所在包及验证批次。
   - 完成标准：范围内每个文件都已读完；清单中每项都能直接实施，或已归入待决、发现。没有可实施项时，直接进入第 6 步报告。
3. **基线**
   - 在任何修改前，按已确定的验证范围运行并记录 `go build`、`go vet`、`go test`，跳过需要连接外部网络或数据库的测试；仓库已配置 staticcheck 或 golangci-lint 时一并记录。缺少的工具只记录，不安装。
   - 完成标准：每条验证命令的基线结果都已记录，已有的失败标为既有失败。
4. **分阶段实施，按风险验证**
   - 改动涉及分支、边界值或集合语义时，检查相关测试的输入与断言是否覆盖受影响的行为。确有行为断言缺口时，在改写前的实现上补并运行 characterization test，固定现有输出或副作用，保留测试及其结果作为比较依据；改名、注释、格式调整不补测试。
   - 覆盖率只辅助定位未执行的语句，不能代替分支、边界、nil 和执行顺序的语义断言。仅在需要时读取现有 profile，或用 `go test -coverprofile` 和 `go tool cover -func` 生成、查看。
   - 按依赖次序执行清单，跨阶段的依赖项整体实施；默认按以下阶段组织：
     1. 删除已证明无用的声明、计算、分支和重复路径；
     2. 控制流、提前返回、作用域；
     3. 返回表达式、字面量、类型转换、循环等局部写法；
     4. 命名、`any`、注释、import、`gofmt`。
   - 已满足等价前提的候选按风险分批，混合风险项按最高风险验证。语义敏感的改动（删除调用或声明、控制流、作用域、类型转换、循环改写，以及其他涉及求值顺序或生命周期的改动）按批单独验证相关包；低风险改动（未导出符号与 receiver 改名、注释、import、`any`）可合批。
   - 验证标准：编译和静态检查没有新增失败或诊断（既有诊断减少属于改善，在报告里记录）；测试结果与基线逐条相同，既有失败的测试变为通过也说明行为变了，需要查明。未通过时，修正或撤回这一批的改动。
   - 完成标准：清单中的可实施项都已实施，并通过所在批次的验证。
5. **复核**
   - 通读完整 diff，确认每处改动都有阅读收益，并能重新说出等价理由；说不出来的撤回，改列为待决。
   - 结构改动带出的新清理机会，只在受影响的函数内处理，加入清单后按第 4 步执行。
   - 对最终状态做完整验证；已有结果仍覆盖当前状态时直接复用。
   - 完成标准：每处改动都有收益和等价理由，最终状态已通过完整验证。
6. **报告**
   - 按下方模板交付；零改动时明确说明，未运行检查不能表述为验证通过。
   - 完成标准：每个已实施的类别、全部待决、全部发现、已执行命令的实际基线与结束结果都已写入；未执行的检查注明原因。

## 报告模板

```markdown
## 结果
<范围、是否实施改动、验证结论；工作区原有的用户改动（如有）>

## 已实施
- <类别>：<一句话概括，涉及的文件>；不明显的改动单独写出等价理由

## 待决
- `<文件:行>` <建议改动> — <需要判断的原因>

## 发现（未修改）
- `<文件:行>` <现象> — <影响>

## 验证
- <命令>：基线 <结果> → 结束 <结果>
- 跳过：<检查> — <原因>
```
