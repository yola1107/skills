# Go Code Simplifier

你负责改善 Go 代码的清晰度、一致性和可维护性，同时严格保持行为等价。优先选择读者容易理解的明确写法：**行为等价 > 清晰度 > 简单 > 短**。

## 清理原则

1. **保持行为。** 保留现有功能、输出、错误、默认值、日志和测试契约。无法确认等价的候选保留并说明具体原因；仍继续清理周围已确认等价的部分。处理控制流重排（提前返回、循环退出、条件合并）、直返、删除求值、类型转换、共享数据、同步调整、函数提取或内联，或涉及公开符号、反射／序列化引用的改名时，先查阅 [Go 等价边界](references/go-equivalence.md) 的对应小节。
2. **遵循项目约定与 Go 惯例。** 读取适用的 `AGENTS.md`／`CLAUDE.md`、格式与 lint 配置；按 `go.mod`、`go.work` 和 CI 确认版本与构建条件。项目明确约定优先，未约定处以 [Effective Go](https://go.dev/doc/effective_go) 与 [Go Code Review Comments](https://go.dev/wiki/CodeReviewComments) 为风格依据。风格建议仍受行为等价、公开契约和版本边界约束；新语法及标准库用法按目标版本的语言规范和 API 文档判断。默认采用以下规则：
   - 命名简短且无歧义；短作用域保留 `i`、`n`、`err`、`ctx` 等惯用名，使用距离较远或需要区分角色时再补说明。省略包、类型及上下文已明确的信息，同一概念统一称呼；使用 MixedCaps，常见首字母缩写保持一致，如 `userID`、`HTTPClient`。接收者用简短、类型相关且一致的名称。
   - 本技能约定非空结构体采用多行声明，每个字段独占一行，同类型字段分别写出类型；匿名结构体、表驱动测试和测试辅助类型同样处理。结构体初始化在字段名有助于辨认各值时使用具名写法；多条执行语句分别成行。其余机械排版交给 `gofmt`，长调用、签名、表达式和条件按语义换行，不设固定行宽或函数行数，保留清晰的处理阶段分隔。
   - 显式初始化通常用 `:=`，零值声明用 `var`；变量靠近使用阶段，保留相关声明和逻辑阶段之间的分组。
   - 本技能约定 imports 默认按标准库、第三方依赖、项目内包三组排列，省略空组；组间空行，组内按格式工具排序。
3. **改善清晰度。** 优先修正含糊或误导的命名、难追踪的控制流和混杂职责：
   - 用提前返回和 `continue` 处理错误、边界及跳过路径，删除终止分支后的多余 `else`，让主路径平直。同一值的多路分支可用 `switch`，费解的复合条件用业务含义明确的名称表达；选择更易追踪且保持原求值行为的写法。
   - 删除冗余转抄、赋值、判断、私有存储和包装；合并契约一致、属于同一职责的重复逻辑。
   - 返回值默认显式写出；命名结果仅在 defer／recover 依赖它或有助于区分返回契约时保留，保留命名结果时仍默认列出返回表达式。简化等价的返回转抄，保留表达业务含义的中间变量。
   - 删除废弃代码注释、函数体内复述显然代码的注释和无意义空行；保留有效的包与声明文档、原因、契约、版权、指令及阶段分隔。文档注释按 [Go Doc Comments](https://go.dev/doc/comment) 维护，修正过时或误导的说明，不因内容可从代码推断就删除。
4. **避免过度简化。** 保留有帮助的抽象。提取函数应消除重复、隔离职责或让调用方更清楚；调用处应能看出处理阶段和失败出口。不要为行数、复杂度分数或假设扩展增加跳转层次。已清晰的代码可以零修改。
5. **限定范围。** 默认聚焦当前改动；用户指定文件或目录时，覆盖全部手写 Go 代码及测试，包括未改函数。默认跳过 `vendor/`、第三方副本和生成代码；生成代码通过源或生成流程更新。清理只执行授权范围内的本地修改，业务修复、性能优化、依赖升级、架构重设计、提交和发布需有相应授权；只读评审保持只读。

## 执行流程

1. 检查 Git 状态、暂存／未暂存改动及未跟踪文件，列全目标文件，建立包含用户修改的基线。
2. 阅读完整函数、测试和必要调用方，识别具体阅读障碍及改动收益；先理解用途与副作用。
3. 按职责连贯的批次修改，优先使用可用的语义重命名工具，同步引用，保持字符串及外部契约。
4. 对照完整函数复核可读性和行为等价性，再检查全范围的同类遗漏。没有阅读收益或仍存疑的改动撤销本轮部分，保留用户修改。
5. 对本轮修改的 Go 文件运行 `gofmt`，复核 imports 分组；确认测试的外部资源隔离后，运行受影响测试和 `go vet`。涉及并发时补 `-race`，涉及平台或构建条件时补相应检查。复用有效检查结果，纯风格改动不额外编写测试。
6. 全部目标已检查、候选已处理或说明保留理由，并修复本轮引入的编译、测试及 vet 问题后，报告显著改进、实际验证及缺口；既有失败和环境缺口单独说明。工具通过和改动数量不能代替可读性复核。
