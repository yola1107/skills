# Go Code Simplifier

在指定范围内降低 Go 代码的理解负担，保持现有行为。取舍顺序：**行为等价 > 清晰 > 显式 > 简单 > 短**。每处改动都要能用一句话说清读者省了什么（少一层嵌套、少记一个变量、少读一段重复逻辑），说不清就不改；已经清楚的代码保持原样。

以项目规则（AGENTS.md、CLAUDE.md、lint 与 goimports 配置）为准，未规定的部分参考 [Effective Go](https://go.dev/doc/effective_go)、[Go Code Review Comments](https://go.dev/wiki/CodeReviewComments) 和 [Go Doc Comments](https://go.dev/doc/comment)。新语法、标准库 API 和循环变量语义，以文件实际生效的 Go 版本为准；排版交给 `gofmt`。

## 可观察行为

改动前后，以下内容保持一致：

- 返回值、错误身份与文本、错误包装方式（`%v`/`%w`）、失败路径的部分返回值、panic。
- 对外调用（RPC、数据库、消息推送、定时任务）的参数、次数和顺序。
- 日志的级别、文本和字段，包括写错的格式串。
- 锁的对象、临界区内的有效语句和加锁顺序；goroutine、defer 和资源的生命周期。
- 导出标识符、接口签名、导出的 struct 字段名与 tag，以及通过反射、字符串注册或配置引用的名字（路由、RPC 方法名、表名）。参数名和结果名不属于签名，按类型注册的 handler 不受影响。
- 求值次数与顺序、短路、nil 与空集合、切片的共享与容量、浮点舍入。

## 改动分类

- **等价改动**：只读当前函数就能证明等价的，直接做。依赖函数外事实的（被调函数有无副作用、引用、接口实现），按 [等价前提](references/go-equivalence-pitfalls.md) 的对应章节查证后做，报告里写一句依据。
- **待决改动**：有收益，但会触碰「可观察行为」或前提查不清，只列出、不实施。包括：
  - 改名或删除导出标识符、导出或带 tag 的字段、错误文本、反射或字符串引用的名字。
  - 增删、移动或重排临界区内的有效语句。
  - 依赖运行时不变量的改写（例如假设两个 id 总是相等）。
  - 看起来多余、但可能有作用的代码，按 Chesterton's fence 处理（例如空的加锁/解锁对）。
  - 只有写测试才能证明等价的改写。
- **发现**：按「缺陷清单」找到的问题。代码保持原样，写进报告。

## 简化清单

按收益从高到低排列，示例见 [examples.md](references/examples.md)。这些写法用于解决具体阅读问题，不用来遍历整包统一风格：`interface{}` 改 `any`、receiver 改名这类改动，只在本来就要改的函数里做，项目强制或用户要求时例外。

1. **控制流**：`if`/`for`/`switch`/`select` 嵌套不超过 3 层（函数体顶层为第 0 层，函数字面量重新计数），单个分支或循环体不超过约 20 行。超出时依次尝试：
   1. 错误、边界和要跳过的情况先 `return`/`continue`，去掉其后的 `else`。
   2. 同一变量三个以上的比较分支改 `switch`。
   3. 仍然超出时，把能起名的独立步骤提取为方法，只调用一次也可以。一长串字段赋值不提取。

   加锁区域内的有效语句和锁的配对保持不变。
2. **冗余**：删除已证明无用的声明、赋值、计算、分支和注释掉的代码，包括首次读取前就被覆盖的初始化、结果没人读的计算。
3. **重复**：输入、失败路径、执行顺序和职责都相同的代码块才合并；只是长得像的保持原样。
4. **作用域**：声明移到首次使用处或使用它的块内；只在 `if`/`switch` 里用的值放进初始化语句。只把 `var` 改成 `:=` 而位置不动，不算收紧作用域。
5. **错误处理**：错误分支里有日志等其他语句时，保持「在 `if` 内处理并显式 `return`」，`err` 只在 `if` 里用时调用留在初始化语句里。错误分支只有 `return err` 时，`if err != nil { return err }; return nil` 合并为 `return err`。
6. **返回值**：有多个返回点或较长的函数，命名结果加裸 `return` 改为显式返回；结果名能说明同类型结果的含义时保留名字。删除结果属于改签名，只在函数未导出、调用点都在范围内、不用于满足接口也不作为函数值时做。
7. **命名**：
   - 修正误导或职责不清的名字（`data`、`tmp`、`ret`、`_x`、`ok1`/`ok2`）。
   - 名字长短与作用域相称，保留 `i`、`k`/`v`、`err`、`ctx`、`ok` 等惯用短名。
   - 用 MixedCaps 和 `ID`/`URL` 等惯用缩写。
   - 布尔值读起来像判断（`hasBet`），数值带单位（`delayMs`），同一概念用同一个名字。
   - 局部名不遮蔽内置名和用到的包名。
   - 同类型的 receiver 保持一致，沿用项目写法（如 `this`）。
8. **现代写法**：仅在更易读且语义相同时采用：
   - 1.18+：`any`、`strings.Cut`
   - 1.21+：`min`/`max`、`slices`、`maps`
   - 1.22+：整数 range，省去循环变量副本
9. **注释**：删除复述代码的说明，修正与代码矛盾的文字，保留原因、契约、工具指令和阶段分隔。新写或修正的 doc comment 以声明名开头。

不为变短而牺牲可读性：一行只做一件事；泛型、interface 只在多个调用点都受益时引入；提取的函数要能起一个说清职责的名字，起不出来就不提取。

## 缺陷清单

逐个函数检查：

- **锁**：
  - 没有 `defer` 解锁时，加锁与解锁之间有 `return`/`continue`/`break` 或 panic 路径。
  - 持有 `RLock` 时写 map、字段，或通过指针修改共享对象。
  - 同一数据由不同的锁保护，或有的地方不加锁。
  - 持有 `RLock` 时再申请同一把锁的 `Lock`。
  - 持锁期间做 I/O。
  - 同一字段混用 `atomic` 与直接读写。
- **错误**：
  - 出错只记日志，却返回成功（error 或错误码为 nil）。
  - error 被丢弃，或没有检查就被覆盖。
  - `:=` 遮蔽了外层之后还要读的变量。
- **其他**：
  - 日志格式符与参数不符。
  - 硬编码的密码、token、DSN、公网 IP。
  - 注释描述的才是本意，代码却写错了。
  - 写入可能为 nil 的 map。
  - 下标访问前没有检查长度。

每条发现标注严重程度：**严重**（死锁、竞态、金额或状态错误、安全）、**一般**（错误被吞、日志错误、边界问题）、**轻微**（拼写、过时注释）。

## 流程

改动留在工作区，由用户审阅 diff 后自行提交；不暂存、不提交、不推送。不写新测试，用户要求时除外。

1. **确定范围**
   - 未指定范围时处理当前改动：
     - `git diff -U0 HEAD -- '*.go'` 的改动行所在的函数（含 doc comment）和函数外的改动行。
     - `git ls-files --others --exclude-standard -- '*.go'` 列出的未跟踪文件，整个处理。
     - 没有改动时询问范围。
   - 指定文件或目录时，处理其中全部手写 Go 代码和测试。
   - 跳过 `vendor/`、`testdata/` 和生成代码（`// Code generated ... DO NOT EDIT.`）。
   - 读 `go.mod`（module 路径、go 版本）和项目规则；从 Makefile、CI 和 lint 配置找到验证入口。

   完成标准：列出要处理的函数（或文件）和受影响的包。
2. **基线**
   - 在测试中搜索 DSN、URL、IP，确认会连接外部服务的测试用 `-skip` 排除。
   - 在任何修改前跑一次「验证」的命令，记下结果。
   - 项目配置了 golangci-lint 时，把范围内的诊断当作候选和发现的线索，仍逐条判断；不要带 `--fix`，也不要运行 `golangci-lint fmt`。实测它们会在 CRLF 文件的每行之间插入空行。

   完成标准：每条命令都有基线结果，或写明未运行的原因。
3. **逐文件改写**：每个文件依次做三件事：
   1. 逐个读完范围内的函数。对每个函数：
      1. 理清所有返回路径、`defer`、锁和副作用。
      2. 对照「缺陷清单」记录发现。
      3. 按「简化清单」找候选并分类，等价改动当场实施。
   2. 把这个文件需要查证的符号集中查一次。有 gopls 时优先用它查语义引用，字符串、tag 和其他构建标签下的引用另查。查证通过的实施，不通过的列为待决。
   3. 对所在包跑 `go build`（改了 `_test.go` 时用 `go vet`），编译错误当场修正。
4. **复查**：重读每个改过的函数。以下情况仍然存在时补做，或在报告里写明不做的原因：
   - 嵌套或分支长度超过「简化清单」第 1 项的上限。
   - 声明离首次使用很远。
   - 初始化后、首次读取前又被赋值。
   - 只用一次、名字也没有信息量的变量。
   - 多返回点的裸 `return`。
   - 需要修正的名字。
5. **收尾格式**：对改过的文件依次执行：
   1. **空行**：删除代码块开头和结尾的空行，保留分隔逻辑段落的单个空行。
   2. **import 分组**：项目没有 goimports/gci 配置时，按标准库、本项目、第三方分三组，组间空一行。先按「module 路径」或「module 路径/」前缀识别本项目，因为 module 路径可能不含点（如 `go_manwugame`）。剩下的路径中，第一段不含 `.` 且不是 `go.mod` 里依赖模块的为标准库，其余为第三方。别名、`_`、`.` 导入保持原写法。
   3. **gofmt**：运行 `gofmt -w <files>`。

   完成标准：改过的文件 `gofmt -l` 无输出（CRLF 差异除外，见「验证」），import 都符合三组规则。
6. **验证与报告**：重跑基线命令逐项对比：构建和静态检查不能新增失败，测试结果逐条一致，原本失败的变成通过也要查明原因。出现新失败时，定位到具体改动，修正或撤回。最后按「报告模板」输出。

## 验证

```bash
gofmt -l <files>
go build <pkgs>
go vet <pkgs>
go test -skip '<外部依赖测试>' <pkgs>
go test -race -skip '<外部依赖测试>' <pkgs>   # 改动涉及锁、goroutine、channel 时；需要 cgo
```

- 项目配置了 golangci-lint 时一并运行。缺少的工具不安装。
- 未运行的检查（包括 Windows 上常因缺少 cgo 而跑不了的 `-race`）照实记为未运行，不能写成通过。
- Windows 上 `core.autocrlf=true` 时，工作区文件是 CRLF，`gofmt -l` 会全部列出。用 `gofmt -d` 确认差异只有换行符的，不算格式问题。gofmt 写回的 LF 会被 Git 归一化，不会显示为改动。只有 `git ls-files --eol` 显示 `i/crlf` 的文件需要转回 CRLF。

## 报告模板

```markdown
## 简化结果
范围：<N 个文件/函数，M 个包>

### 发现（未修改）
- [严重] `<文件>:<行>` `<函数>`：<问题>。影响：<后果>。修复方向：<一句话>

### 改动
- 汇总：<如"拉平嵌套 6 处、收紧作用域 9 处、改名 12 处">
- `<文件>` `<函数>`：<需要查证的改动>。依据：<查证了什么>

### 待决（未实施）
- `<位置>`：<建议>。原因：<触碰的可观察行为或缺少的前提>

### 验证
- build / vet / test：基线 <结果> → 结束 <结果>
- 排除的测试：<名字及原因>；未运行：<检查项及原因>
```

有严重级别的发现时，在报告第一行提示。没有可做的改动时说明零改动，照常列出发现。用户原有的未提交改动要注明。
