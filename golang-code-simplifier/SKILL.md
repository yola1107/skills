# Golang Code Simplifier

目标：让下一位读者更快看懂代码，行为完全不变。拿不准是否等价的改动不做，写进报告。

## 红线

以下内容在改动前后必须一致，任何一项受影响的改动都归入 C 级（见「分级」），不实施：

- 导出标识符、函数签名、接口方法集、struct 字段名与 tag、错误变量与错误文本。
- 通过反射或字符串引用的名字：框架按方法名注册的 handler/路由、RPC 方法、ORM 表名与列名、模板字段、配置 key。
- 副作用的种类、次数、顺序：数据库、RPC、消息、文件、日志（级别、文本、字段）、指标。
- 并发结构：锁的对象与临界区范围、goroutine 的启动与退出、channel 的关闭时机、`defer` 的执行时机。
- 值的形态：nil 与空切片/空 map、切片的底层数组共享、浮点结果、panic 与否。

不处理：带 `// Code generated ... DO NOT EDIT.` 头的文件、`vendor/`、`testdata/`。不暂存、不提交，改动留在工作区由用户审阅。

## 工作流

复制清单并逐项勾选：

```
- [ ] 1. 确定范围
- [ ] 2. 读取项目约束
- [ ] 3. 基线验证
- [ ] 4. 逐函数找候选并分级
- [ ] 5. 实施 A、B 级改动
- [ ] 6. 最终验证并对比基线
- [ ] 7. 报告
```

**1. 确定范围。** 在仓库内运行：

```bash
go run <本 skill 目录>/scripts/scope.go            # 相对 HEAD 的改动 + 未跟踪文件
go run <本 skill 目录>/scripts/scope.go <路径>...  # 用户指定的文件或目录
```

脚本按 module 分组输出手写 Go 文件、受影响的包和验证命令，已排除生成代码、`vendor/`、`testdata/`。用户未指定范围时，只改改动涉及的函数；范围外看到的问题只报告。

**2. 读取项目约束。** `go.mod` 的 `go` 版本决定可用写法（见「简化清单」第 5 项）；再读 AGENTS.md、CLAUDE.md、`.golangci.yml`、Makefile 和 CI 配置。项目规则与本 skill 冲突时以项目为准。

**3. 基线验证。** 在改动前对受影响的包跑「验证」中的命令并记下结果。基线已有失败时照实记录，最终只要求不新增失败。

**4. 逐函数找候选并分级。** 完整读完一个函数（所有返回路径、`defer`、锁、调用的副作用）再动它。按「简化清单」找候选，每个候选分级：

- **A 级**：局部改写，读当前函数即可证明等价。直接做。
- **B 级**：等价性依赖函数外的事实，需要查引用、读被调实现或核对 [traps.md](references/traps.md) 对应小节。查证后做，报告里写一句等价依据。
- **C 级**：可能触碰红线、影响范围外代码，或前提无法确认。不做，列入报告「建议」。
- **缺陷**：bug、竞态、被丢弃的 error、`:=` 意外遮蔽外层变量、注释与代码矛盾。不修，列入报告「发现」。

每处改动都要能用一句话说清读者省了什么（少一层嵌套、少记一个变量、少读一段重复逻辑）。说不出来就不改；本来就清楚的代码保持原样。

**5. 实施。** 先做 A 级，再做 B 级；改完用 `gofmt`（项目用 goimports 时用 goimports）格式化改动文件。修改分支逻辑而现有测试没有覆盖时，先在原实现上补表驱动测试锁定当前行为并跑通，再改写。

**6. 最终验证。** 重跑与基线相同的命令逐项对比。出现新失败时定位到具体改动，修正或撤回。

**7. 报告。** 按「报告模板」输出。

## 简化清单

按收益从高到低排列，具体写法与反例见 [patterns.md](references/patterns.md)。

1. **控制流**：错误和边界条件先返回；`return`/`continue` 之后去掉 `else`；循环体内用 `continue` 代替整段包在 `if` 里；三个以上同一变量的比较分支改 `switch`。
2. **冗余**：未使用的赋值、永远为真或为假的条件、注释掉的代码、`len` 之前多余的 nil 判断、`delete` 之前多余的存在判断、只转发一次的中间变量。
3. **作用域**：变量声明移到首次使用处；只在 `if`/`switch` 内使用的值放进初始化语句；缩短贯穿整个函数的临时状态。
4. **错误处理**：同一函数内包装风格统一为 `fmt.Errorf("动作: %w", err)`，前提是不改已有错误文本；`if err != nil { return err }; return nil` 合并为 `return err`（`err` 为 `error` 类型时）。
5. **标准库写法**，以文件生效的 Go 版本为准：

   | 版本 | 可用写法 |
   |------|----------|
   | 1.18+ | `any`、`strings.Cut`、`bytes.Cut` |
   | 1.21+ | `min`、`max`、`clear`、`slices`、`maps` |
   | 1.22+ | `for i := range n`、去掉循环变量副本 `v := v`、`cmp.Or` |

6. **命名**：修正误导性的局部变量、参数和未导出标识符；缩写全大写（`ID`、`URL`、`HTTP`）；同一类型的 receiver 名一致。导出名与包名重复（`user.UserInfo`）属于导出改名，列为 C 级建议。
7. **注释**：删除复述代码的注释；保留解释原因、约束、契约、`//go:`/`//nolint` 等指令的注释；修正后的 doc comment 以标识符名开头。

## 不要做

- 为了少几行写嵌套闭包、长链式调用，或把多个操作塞进一行。
- 为一两个调用点新增泛型、interface、helper 或 option 模式。
- 合并只是长得像、但失败处理或调用顺序不同的两段代码。
- 把清楚的长函数切成一串只调用一次、名字说不出职责的小函数。
- 在不改的函数里做全包统一风格的批量改写（`interface{}` → `any`、receiver 改名、import 重排），除非用户明确要求。
- 修复发现的缺陷。修复会改变行为，交给用户决定。

## 验证

在 scope.go 输出的 module 目录下运行，`<pkgs>` 和 `<files>` 取自脚本输出：

```bash
gofmt -l <files>
go build <pkgs>
go vet <pkgs>
go test <pkgs>
go test -race <pkgs>   # 改动涉及 goroutine、锁或 channel 时；需要 cgo
```

项目配置了 golangci-lint 或 staticcheck 时一并运行。缺少的工具不安装，报告中注明。需要真实数据库、外部网络的测试跳过并说明原因。Windows 下 CRLF 文件会被 `gofmt -l` 全部列出，用 `gofmt -d` 确认差异是否只有换行符。

## 报告模板

```markdown
## 简化结果

范围：<N 个文件，涉及 M 个包>

### 改动
- `<文件>` `<函数>`：<改了什么，读者省了什么>。[A]
- `<文件>` `<函数>`：<改了什么>。[B] 等价依据：<查证了什么>

### 建议（C 级，未实施）
- `<位置>`：<建议>。未实施原因：<触碰哪条红线或缺少什么前提>

### 发现（未修改）
- `<位置>`：<缺陷描述与影响>

### 验证
- go build：基线 <结果> → 结束 <结果>
- go vet：基线 <结果> → 结束 <结果>
- go test：基线 <结果> → 结束 <结果>
- 未运行：<检查项及原因>
```

没有可做的改动时直接说明零改动，并照常列出建议与发现。未运行的检查不能写成通过。
