# Golang Code Simplifier

目标：让下一位读者更快看懂代码，行为完全不变。拿不准是否等价的改动不做，写进报告。

## 红线

以下内容在改动前后必须一致，任何一项受影响的改动都归入 C 级（见「分级」），不实施：

- 导出标识符、接口方法集、struct 字段名与 tag、错误变量、错误文本与错误包装方式（`%v`/`%w`）。
- 函数签名：参数与结果的类型、个数和顺序。结果名不属于函数类型，去掉或改名命名结果不算改签名（前提见 traps.md「返回值」）。
- 通过反射或字符串引用的名字：框架按方法名注册的 handler/路由、RPC 方法、ORM 表名与列名、模板字段、配置 key。
- 副作用的种类、次数、顺序：数据库、RPC、消息、文件、日志（级别、文本、字段）、指标。
- 并发结构：锁的对象与临界区范围、goroutine 的启动与退出、channel 的关闭时机、`defer` 的执行时机。
- 值的形态：nil 与空切片/空 map、切片的底层数组共享、浮点结果、panic 与否。

不处理：带 `// Code generated ... DO NOT EDIT.` 头的文件、`vendor/`、`testdata/`。不暂存、不提交，改动留在工作区由用户审阅。

## 工作流

复制清单并逐项勾选：

```
- [ ] 1. 确定范围
- [ ] 2. 读取项目约束
- [ ] 3. 基线验证
- [ ] 4. 逐函数找候选、分级，并做缺陷扫描
- [ ] 5. 实施 A、B 级改动并补测试
- [ ] 6. 收益复查
- [ ] 7. 收尾格式：空行、import 分组、gofmt、换行符
- [ ] 8. 最终验证并对比基线
- [ ] 9. 报告
```

**1. 确定范围。** 在仓库内运行：

```bash
go run <本 skill 目录>/scripts/scope.go            # 相对 HEAD 的改动 + 未跟踪文件
go run <本 skill 目录>/scripts/scope.go <路径>...  # 用户指定的文件或目录
```

脚本按 module 分组输出手写 Go 文件、受影响的包和验证命令，排除生成代码、`vendor/`、`testdata/`（显式传入这些路径也会排除）。它还会列出：被删除或移走的文件（此时 build 和 vet 覆盖 `./...`，以发现断掉的引用）、已没有 Go 文件的包、CRLF 换行的文件、疑似依赖外部服务的测试及对应的 `-skip` 参数。用户未指定范围时，只改改动涉及的函数；范围外看到的问题只报告。

**2. 读取项目约束。** `go.mod` 的 `module` 路径决定 import 分组，`go` 版本决定可用写法（见「简化清单」第 7 项）；再读 AGENTS.md、CLAUDE.md、`.golangci.yml`、goimports/gci 配置、Makefile 和 CI 配置。项目规则与本 skill 冲突时以项目为准。

**3. 基线验证。** 先读 scope.go 列出的疑似外部依赖测试，确认会连接数据库、网络或第三方服务的，用 `go test -skip` 排除；连接非本机地址的测试一律不运行。然后在改动前对受影响的包跑「验证」中的命令并记下结果，基线与最终验证使用同一组参数。基线已有失败时照实记录，最终只要求不新增失败。

**4. 逐函数找候选、分级，并做缺陷扫描。** 完整读完一个函数（所有返回路径、`defer`、锁、调用的副作用）再动它。读的同时按「缺陷扫描」逐项检查，按「简化清单」找候选，每个候选分级：

- **A 级**：局部改写，读当前函数即可证明等价。直接做。
- **B 级**：等价性依赖函数外的事实，需要查引用、读被调实现或核对 [traps.md](references/traps.md) 对应小节。查证后做，报告里写一句等价依据。
- **C 级**：可能触碰红线、影响范围外代码，或前提无法确认。不做，列入报告「建议」。
- **缺陷**：「缺陷扫描」命中的问题。不修，列入报告「发现」。

每处改动都要能用一句话说清读者省了什么（少一层嵌套、少记一个变量、少读一段重复逻辑）。说不出来就不改；本来就清楚的代码保持原样。

**5. 实施并补测试。** 先做 A 级，再做 B 级。测试证据要覆盖实际改动的路径：

- 改动分支、边界值或集合语义而现有测试没有覆盖时，先在原实现上补表驱动测试锁定当前行为并跑通，再改写。
- 改动的路径上有金额计算、数据库、RPC、消息推送时，测试要断言这些调用的参数、次数和顺序（用记录调用的替身实现）。只测到提前返回的分支，不能作为这类改写的等价证据。
- 无法构造替身、关键路径测不到时，把该改动降为 C 级；确需保留时，在报告「测试覆盖」中明确列为未验证。
- 新增的测试放在单独的文件里，报告中列出。

**6. 收益复查。** 按最终代码重读每个改动过的函数，找出遗漏并按分级补做，补做后的改动同样需要验证：

- 仍有三层以上的嵌套，或可以用提前返回展平的大块 `if`。
- 变量声明离首次使用仍然很远，中间隔着不相关的逻辑。只把 `var` 换成 `:=` 而位置不动，不算收紧作用域。
- 重复初始化：变量初始化后、首次读取前又被重新赋值（例如先 `x := make([]T, 0)`，后面使用前又 `x = make([]T, 0)`）。
- 只被读一次、名字也没有提供额外信息的局部变量，始终为同一个值的变量。
- 可以用「简化清单」第 6 项处理的返回值。

**7. 收尾格式。** 对每个改动过的文件依次执行：

1. **空行**：删除代码块开头（`{` 之后）和结尾（`}` 之前）的空行，连续空行压成一个，保留分隔逻辑段落的单个空行。范围是整个文件或目录时处理整个文件；否则只处理改动过的函数。
2. **import 分组**：项目没有 goimports/gci 配置时，整个 import 块分成三组，顺序为标准库、本项目、第三方，组间空一行，组内顺序交给 gofmt。归组规则：
   - 本项目：路径等于 `go.mod` 的 module 路径，或以「module 路径 + `/`」开头。先判断这一条，因为 module 路径可能不含点（如 `go_manwugame`）。
   - 标准库：其余路径中，第一段不含 `.` 的。
   - 第三方：其余全部。
   - 别名、`_`、`.` 导入保留原写法，按路径归组；import 上方或行尾的注释随该行移动；`import "C"` 和它前面的 cgo 注释保持单独声明不动。
   - 构建所用工具链早于 Go 1.21 时，调整 import 顺序可能改变包初始化顺序（见 traps.md「import」），此时不调整分组，在报告中注明。
3. **gofmt**：运行 `gofmt -w <files>`。不要在之后运行不带项目配置的 goimports，它的分组规则与上面不同。
4. **换行符**：`gofmt` 输出 LF，scope.go 列为 CRLF 的文件转回 CRLF，避免整个文件显示为改动。

**8. 最终验证。** 重跑与基线相同的命令逐项对比。出现新失败时定位到具体改动，修正或撤回。

**9. 报告。** 按「报告模板」输出。

## 缺陷扫描

缺陷扫描与简化同等重要。读每个函数时逐项检查，命中的写进报告「发现」，代码保持原样：

- **锁**：
  - 没有配 `defer` 的 `Lock()`/`RLock()`，检查它到 `Unlock()`/`RUnlock()` 之间每条 `return`、`continue`、`break` 和可能 panic 的路径，确认都会解锁。
  - 在 `RLock` 下写 map 或字段。
  - 同一个 map 或字段在不同函数里由不同的锁保护，或有的地方不加锁读写。
- **错误**：
  - 错误分支只记日志就返回，但返回值仍表示成功（error 为 nil、错误码对象为 nil），调用方会按成功处理。
  - `err` 被赋值后没有检查就被覆盖。
  - `:=` 遮蔽了外层随后还要读的变量。
- **格式串**：项目自定义的 `Xxxf` 日志或错误函数，格式符的数量和类型与参数一致。`go vet` 识别不了大多数自定义包装函数。
- **敏感信息**：代码和测试里硬编码的密码、token、DSN、公网 IP。
- **注释**：注释描述的行为与代码相反或已过时。
- **其他**：向可能为 nil 的 map 写入、未检查长度的下标访问、循环里的 `defer`、没有退出条件的 goroutine。

每条发现标注严重程度：**严重**（死锁、数据竞争、金额或状态错误、安全问题）、**一般**（错误被吞、日志错误、边界缺陷）、**轻微**（拼写、过时注释）。改动前就存在的缺陷另标「原有」，提示用户单独修复。

## 简化清单

按收益从高到低排列，具体写法与反例见 [patterns.md](references/patterns.md)。

1. **控制流**：错误和边界条件先返回；`return`/`continue` 之后去掉 `else`；循环体内用 `continue` 代替整段包在 `if` 里；三个以上同一变量的比较分支改 `switch`。
2. **冗余**：未使用的赋值、永远为真或为假的条件、注释掉的代码、`len` 之前多余的 nil 判断、`delete` 之前多余的存在判断、只转发一次且名字没有提供额外信息的中间变量、首次读取前就被覆盖的初始化。
3. **重复**：输入、副作用、执行顺序都相同的重复代码块，提取为名字能说明职责的函数（B 级）。长函数里的重复块同样处理，不因函数长、改动大就整体放弃；只是长得像的代码见「不要做」。
4. **作用域**：变量声明移到首次使用处；只在一个分支或循环里用到的变量，声明移进该块；只在 `if`/`switch` 内使用的值放进初始化语句；缩短贯穿整个函数的临时状态。
5. **错误处理**：保留已有的错误包装语义，`%v`、`%w`、`errors.New` 和错误文本都不改；`if err != nil { return err }; return nil` 合并为 `return err`（`err` 的静态类型为 `error` 时）。
6. **返回值**：
   - 命名结果加裸 `return`：函数有多个返回点或较长时，改为显式返回；短函数可以保留。同类型的多个结果靠名字说明含义时（如 `(min, max int)`），保留结果名，只把裸 `return` 改成显式。`defer`/`recover` 读写结果时保持原样。
   - 结果始终为同一个值，或所有调用方都忽略某个结果：删除它属于改签名。函数未导出、所有调用点都在范围内一起修改、没有用于满足接口或作为函数值传递时为 B 级，否则为 C 级。
7. **标准库写法**，以文件生效的 Go 版本为准：

   | 版本 | 可用写法 |
   |------|----------|
   | 1.18+ | `any`、`strings.Cut`、`bytes.Cut` |
   | 1.21+ | `min`、`max`、`clear`、`slices`、`maps` |
   | 1.22+ | `for i := range n`、去掉循环变量副本 `v := v`、`cmp.Or` |

8. **命名**：修正误导性的局部变量、参数和未导出标识符；缩写全大写（`ID`、`URL`、`HTTP`）；同一类型的 receiver 名一致。导出名与包名重复（`user.UserInfo`）属于导出改名，列为 C 级建议。
9. **注释**：删除复述代码的注释；保留解释原因、约束、契约、`//go:`/`//nolint` 等指令的注释；修正后的 doc comment 以标识符名开头。条件取反、分支重排后，同步更新挂在上面的注释。与代码矛盾的注释，已从代码查证本意的直接修正（A 级），无法确定的列入「发现」。

## 不要做

- 为了少几行写嵌套闭包、长链式调用，或把多个操作塞进一行。
- 为一两个调用点新增泛型、interface、helper 或 option 模式。
- 合并只是长得像、但失败处理或调用顺序不同的两段代码。
- 把清楚的长函数切成一串只调用一次、名字说不出职责的小函数。
- 在不改的函数里做全包统一风格的批量改写（`interface{}` → `any`、receiver 改名），除非用户明确要求。import 分组和 gofmt 按第 7 步处理。
- 删除错误分支末尾的 `return`。`if err != nil { log(err); return }; return` 去掉第一个 `return` 虽然等价，但以后在函数末尾追加的代码会在出错时执行。
- 同一文件内只改一部分函数的返回风格（命名结果加裸 `return` 与显式返回）。范围是整个文件或目录时，文件内同类函数一起改；范围只是改动涉及的函数时，沿用文件原有风格。
- 修复发现的缺陷。修复会改变行为，交给用户决定。

## 验证

在 scope.go 输出的 module 目录下运行，`<pkgs>` 和 `<files>` 取自脚本输出：

```bash
gofmt -l <files>
go build <pkgs>        # 有删除或移动文件时为 ./...
go vet <pkgs>          # 同上
go test -skip '<外部依赖测试>' <pkgs>
go test -race -skip '<外部依赖测试>' <pkgs>   # 改动涉及 goroutine、锁或 channel 时；需要 cgo
```

- 项目配置了 golangci-lint 或 staticcheck 时一并运行。缺少的工具不安装，报告中注明。
- 没有外部依赖测试时省略 `-skip`；`-skip` 需要 Go 1.20+ 工具链，更早的工具链改用 `-run` 只列出要运行的测试。被排除的测试在报告中逐个列出。
- `-race` 在 Windows 上可能因缺少 gcc 或 ThreadSanitizer 初始化失败而无法完成，此时记为未运行，不能记为通过。
- Windows 下 CRLF 文件会被 `gofmt -l` 全部列出，用 `gofmt -d` 确认差异是否只有换行符。

## 报告模板

```markdown
## 简化结果

范围：<N 个文件，涉及 M 个包>

### 发现（未修改，按严重程度排序）
- [严重][原有] `<文件>:<行号>` `<函数>`：<缺陷描述>。影响：<会导致什么>。修复方向：<一句话>

### 改动
- `<文件>` `<函数>`：<改了什么，读者省了什么>。[A]
- `<文件>` `<函数>`：<改了什么>。[B] 等价依据：<查证了什么>

### 测试覆盖
- `<函数>`：关键路径 <改动涉及的分支与副作用>；对应测试 <测试名，或"无">；未验证 <没有被测试断言的部分，或"无">

### 建议（C 级，未实施）
- `<位置>`：<建议>。未实施原因：<触碰哪条红线或缺少什么前提>

### 新增测试
- `<文件>`：<锁定了哪些行为>。可保留作为回归测试，也可在审阅后删除。

### 验证
- go build：基线 <结果> → 结束 <结果>
- go vet：基线 <结果> → 结束 <结果>
- go test：基线 <结果> → 结束 <结果>
- 排除的测试：<测试名及原因>
- 未运行：<检查项及原因>
```

有严重级别的发现时，在报告第一行用一句话提示。没有可做的改动时直接说明零改动，并照常列出发现与建议。未运行的检查不能写成通过。
