# Golang Code Simplifier

基于 [Anthropic 官方 code-simplifier](https://github.com/anthropics/claude-plugins-official/blob/main/plugins/code-simplifier/agents/code-simplifier.md) 的 Go 版本。按项目规范清理代码，优先采用直白、易读的实现。

## 原则

1. **保留行为**：只改变实现，保持输出、错误、日志和副作用不变。保持导出 API 的名称和函数类型、协议字段及框架约定不变；其余内部名称按用途审查。原有确定性 bug 只报告位置、触发条件和影响，不主动修复。
2. **遵循 Go 规范**：遵循 [Uber Go Style Guide](https://github.com/uber-go/guide/blob/master/style.md)，适用的 AGENTS.md、CLAUDE.md 和本 skill 的明确约定覆盖冲突。同时参考 [Effective Go](https://go.dev/doc/effective_go)、[Go Code Review Comments](https://go.dev/wiki/CodeReviewComments) 和 [Go Doc Comments](https://go.dev/doc/comment)。
   - 新语法、标准库 API 和循环变量语义，以文件实际生效的 Go 版本为准；排版交给 `gofmt`，import 按标准库、本项目、第三方分组。
   - 标识符使用 `MixedCaps`/`mixedCaps`，缩略词保持全大写或全小写，同一概念命名一致；接收者通常取类型核心含义的一个字母，同一类型保持一致。
   - 将不清晰的裸 `return` 改为显式返回，保留有实际用途的命名返回值。
3. **提升清晰度**：按下方检查项整理命名、控制流、职责和冗余，使主流程清楚、职责明确。
4. **保持平衡**：以理解成本判断收益，保留有价值的抽象，采用清楚的条件和普通写法；不以行数、嵌套深度或函数数量单独判断质量。
5. **聚焦范围**：默认处理近期改动涉及的完整函数、闭包及相关声明；指定文件或目录时，覆盖全部手写 Go 代码，包括 `_test.go`。

## 清理检查

- **命名**：通读定义和用途，检查字段、参数、局部变量、函数/方法及接收者，列出需调整或保留的名称与位置。修正拼接词、含义不明的缩写和无解释的数字后缀，名称应表达业务含义；惯用的 `i`、`err`、`ctx` 和真实序号可保留。
- **退出分支**：先处理错误、边界和无需继续的情况；分支已退出且不会到达后续语句时移除 `else`。成功路径受 `if` 初始化作用域限制时，调整声明位置并保持变量绑定。
- **连续条件**：无中间语句和独立 `else` 的共同前提可按原顺序合并为 `&&`；清理可证明多余的判断、双重否定和布尔回填，复杂条件保持易读。
- **重复分支**：结合已知分支条件集中等价动作、赋值、返回及共同前后缀，保持条件与副作用的先后关系。默认值加条件覆盖仅在新增求值也等价时采用。
- **循环流程**：用 `continue` 筛掉无需处理的项，顺序展开有效项处理；简化仅用于延迟退出的标志和中转结果，保留本轮收尾与跨迭代状态。
- **分支选择**：同一判别对象的分支链可在更清楚时改为 `switch`，合并相同 `case`；保持匹配优先级，独立 `if` 仍可依次执行，对称业务分支可保留 `if/else`。
- **职责**：对混杂归集、计算、选择、执行、收尾等阶段的函数，梳理数据与副作用依赖，再按职责提取或合并。提取应让调用方更简单、参数与状态传递更清楚；新函数内可保留职责必需的分支。随机调用和收尾依赖须落实到具体语句，继续寻找不受影响的整理机会。
- **其余整理**：删除无用声明、赋值、转交层和复述代码的注释，收紧作用域、整理空行；删除声明或计算前确认引用及初始化副作用。

## 等价性核对

按 [Go 语言规范](https://go.dev/ref/spec#Statements) 核对原有路径，重点保持：

- 返回值、错误、日志和副作用的内容、次数与顺序，包括随机调用；保持 nil/空集合形态及具体类型 nil 转为接口后的结果。
- 求值的短路保护和比较语义；仅删改可确认无副作用、值稳定且不影响 `panic` 或阻塞的求值。
- 新增退出后的必做逻辑、解锁和收尾，以及 `break`、`continue`、标签和 `fallthrough` 的目标；引入 `switch` 时核对无标签 `break`。
- `defer`、`recover` 的执行语义，以及命名返回值、外层变量的绑定、读写时机和跨迭代状态；移动声明、缓存读取或提取函数时重新核对。
- 改名涉及的接口实现、构建标签、反射、字符串绑定、序列化和日志中的名称；同步定义与相关引用。

## 执行与验收

1. **定范围与基线**：记录改前状态，选定与影响范围对应的现有构建、静态检查和快速本地测试。
2. **通读并列清单**：覆盖范围内的类型声明、完整函数和闭包，按「清理检查」记录命名遗漏、控制流及职责整理机会的位置和原因。清单只列问题及保留项，不抄录全部标识符。
3. **集中修改**：以同一函数的一组相关改写为一批；跨文件改名或提取时，定义与引用同批完成。涉及退出、求值顺序、随机、锁或 `defer` 的变化随改核对；批次结束重读完整函数及影响处，再统一整理格式。
4. **验证等价**：执行选定检查并与基线对比，注明具体覆盖范围。现有检查未覆盖的行为风险，先观察原实现再补最小验证；仍不能确认等价且验证代价过高时缩小改动或保留。新增失败或超时须修正或撤回后复核。
5. **分别验收**：整包清理由独立 agent 对完整范围只读复核，分别给出以下结论：
   - **行为等价性**：核对改动路径及证据，指出未验证范围；局部对照通过只支持实际覆盖的行为。
   - **清理充分性**：重新检查全部类型声明、函数和闭包，包括无 diff 的部分，按「清理检查」发现新遗漏并逐项核销清单，尤其复查字段、参数、局部变量命名和混杂职责。
   汇总两项的全部遗漏，集中修正后按影响范围重新验证并复核影响处；直至明确且等价的清理机会已处理，或逐项给出位置、具体依赖与保留原因。测试通过不能代替充分性验收。
6. **按实际结果汇报**：报告重要改动、两项验收结论、验证覆盖、跳过项、保留项及原有 bug；两项均完成后才能宣称范围内清理完成。

按需使用现有工具：简单搜索用 `rg`，复杂结构定位可用 ast-grep，类型、引用与改名可用 gopls；复用项目的格式和 lint 配置。搜索命中、诊断或 lint 通过均不能替代完整范围的清理验收，工具不可用时按上下文手工核对。

依赖外部服务或已确认的既有慢测试默认跳过，说明原因和未验证范围；已通过的检查仅因新改动或覆盖缺口追加。清单在工作记录中维护，无需另建报告文件。
