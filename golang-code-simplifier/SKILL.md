# Golang Code Simplifier

## 原则

1. **行为不变**：只改代码怎么写，不改代码做什么。拿不准是否等价的改动不做，写进报告。
2. **项目规范优先**：AGENTS.md、CLAUDE.md、lint 与格式化配置优先于本 skill。
3. **清晰胜过简短**：目标是让下一位读者更快看懂，行数不是收益标准。
4. **有度**：保留有用的抽象和能给步骤命名的中间变量；已经清楚的代码保持原样。
5. **聚焦范围**：默认只处理当前改动；用户指定文件或目录时处理其中全部手写代码。

## 红线

以下内容在改动前后必须一致，受影响的改动归入 C 级（见「分级」），不实施：

- 导出标识符、接口方法集、struct 字段名与 tag、错误变量、错误文本与错误包装方式（`%v`/`%w`）。
- 函数签名：参数与结果的类型、个数和顺序。结果名和参数名不属于函数类型，改名或去掉结果名不算改签名（前提见 traps.md「返回值」）。
- 通过反射或字符串引用的名字：框架按方法名注册的 handler/路由、RPC 方法、ORM 表名与列名、模板字段、配置 key。
- 副作用的种类、参数、次数、顺序：数据库、RPC、消息、文件、日志（级别、文本、字段）、指标。
- 并发结构：锁的对象与临界区范围、goroutine 的启动与退出、channel 的关闭时机、`defer` 的执行时机。
- 值的形态：nil 与空切片/空 map、切片的底层数组共享、浮点结果、panic 与否。

不处理：带 `// Code generated ... DO NOT EDIT.` 头的文件、`vendor/`、`testdata/`。不暂存、不提交，改动留在工作区由用户审阅。

## 模式

- **快速**（默认）：范围是当前改动、单个文件，或写完代码后的收尾。不写新测试，报告精简。
- **深度**：用户指定目录或包，或明确要求全面清理。允许写临时测试（见「等价证据」），报告列出测试覆盖。

两种模式都完整执行下面的工作流和缺陷扫描。

## 工作流

```
- [ ] 1. 确定范围
- [ ] 2. 读取项目约束
- [ ] 3. 基线验证
- [ ] 4. 逐函数阅读、扫描、改写
- [ ] 5. 收益复查
- [ ] 6. 收尾格式
- [ ] 7. 最终验证
- [ ] 8. 报告
```

**1. 确定范围。** 在仓库内运行：

```bash
go run <本 skill 目录>/scripts/scope.go            # 相对 HEAD 的改动 + 未跟踪文件
go run <本 skill 目录>/scripts/scope.go <路径>...  # 用户指定的文件或目录
```

脚本按 module 分组输出手写 Go 文件、受影响的包和验证命令，排除生成代码、`vendor/`、`testdata/`（显式传入也排除），并列出：被删除或移走的文件（此时 build 和 vet 覆盖 `./...`）、已没有 Go 文件的包、CRLF 换行的文件、疑似依赖外部服务的测试及对应的 `-skip` 参数。完成标准：拿到每个 module 的文件、包、外部依赖测试和 CRLF 文件列表。

**2. 读取项目约束。** `go.mod` 的 `module` 路径决定 import 分组，`go` 版本决定可用写法（见「简化清单」第 7 项）；再读 AGENTS.md、CLAUDE.md、`.golangci.yml`、goimports/gci 配置、Makefile 和 CI 配置。

**3. 基线验证。** 确认 scope.go 列出的疑似外部依赖测试中，哪些会连接数据库、网络或第三方服务，用 `-skip` 排除；连接非本机地址的测试一律不运行。然后对受影响的包跑一次「验证」中的命令并记下结果，最终验证使用同一组参数。完成标准：每条命令都有基线结果（通过；失败及失败项；或未运行及原因）。

**4. 逐函数阅读、扫描、改写。** 一次读完一个文件，按函数处理：完整读完一个函数（所有返回路径、`defer`、锁、调用的副作用）后，按「缺陷扫描」检查，按「简化清单」找候选并分级，接着就在该函数里实施 A、B 级改动，再进入下一个函数。

- **A 级**：读当前函数即可证明等价。直接做。
- **B 级**：等价性依赖函数外的事实，需要查引用、读被调实现或核对 [traps.md](references/traps.md) 对应小节。查证后做，报告里写一句等价依据。
- **C 级**：可能触碰红线、影响范围外代码，或前提无法确认。不做，列入报告「建议」。
- **缺陷**：「缺陷扫描」命中的问题。不修，列入报告「发现」。

B 级候选要查的符号集中查一次。查引用、调用关系和改名优先用 gopls（装有 golang-gopls skill 时按它操作）：`gopls rename` 会拦下破坏接口实现的改名；`references` 只覆盖所查文件的构建配置，其他 GOOS 和构建标签下的文件要另查，经由函数值、interface 的调用也不在调用层级里。没有 gopls 时用 grep 加编译检查。

每处改动都要能用一句话说清读者省了什么（少一层嵌套、少记一个变量、少读一段重复逻辑）。改写期间不跑测试。完成标准：范围内每个函数都已读完；每个候选都已实施或定级为 C，每条发现都有位置和严重程度。

**5. 收益复查。** 按最终代码重读每个改动过的函数，以下任一项成立就按分级补做，或在报告中写明不做的原因：

- 嵌套超过「简化清单」第 1 项的上限，或单个分支、循环体仍超过约 20 行且职责独立。
- 变量声明离首次使用仍然很远。只把 `var` 换成 `:=` 而位置不动，不算收紧作用域。
- 重复初始化：变量初始化后、首次读取前又被重新赋值。
- 只被读一次、名字也没有提供额外信息的局部变量；始终为同一个值的变量。
- 第 6 项可处理的返回值，第 8 项要求修正的名字。

**6. 收尾格式。** 对每个改动过的文件依次执行：

1. **空行**：删除代码块开头（`{` 之后）和结尾（`}` 之前）的空行，连续空行压成一个，保留分隔逻辑段落的单个空行。范围是整个文件或目录时处理整个文件；否则只处理改动过的函数。
2. **import 分组**：项目没有 goimports/gci 配置时，整个 import 块分成三组，顺序为标准库、本项目、第三方，组间空一行，组内顺序交给 gofmt。
   - 本项目：路径等于 `go.mod` 的 module 路径，或以「module 路径 + `/`」开头。先判断这一条，因为 module 路径可能不含点（如 `go_manwugame`）。
   - 标准库：其余路径中，第一段不含 `.` 的。
   - 第三方：其余全部。
   - 别名、`_`、`.` 导入保留原写法，按路径归组；import 上方或行尾的注释随该行移动；`import "C"` 和它前面的 cgo 注释保持单独声明不动。
   - 构建所用工具链早于 Go 1.21 时不调整分组（见 traps.md「import」），在报告中注明。
3. **gofmt**：运行 `gofmt -w <files>`。之后不再运行不带项目配置的 goimports，它的分组规则与上面不同。
4. **换行符**：scope.go 列为 CRLF 的文件转回 CRLF，避免整个文件显示为改动。

完成标准：改动文件的 `gofmt -l` 没有输出（CRLF 文件以 `gofmt -d` 只有换行差异为准）；每个改动文件的 import 块都符合三组规则。

**7. 最终验证。** 重跑与基线相同的命令逐项对比。出现新失败时定位到具体改动，修正或撤回。深度模式下的临时测试在这一步之后删除。完成标准：每条命令都有与基线对照的结果，没有新增失败。

**8. 报告。** 按「报告模板」输出。

## 等价证据

- **默认证据是阅读、编译和现有测试。** A 级改动不写新测试。
- **有副作用的路径**（金额、数据库、RPC、消息、日志）上只做 A 级改写：每个调用的触发条件、参数、次数和顺序，都能在函数内逐行对照。需要构造替身才能证明等价的改写降为 C 级，不写替身。
- **快速模式**不写测试；只有测试才能确认的改动降为 C 级。
- **深度模式**下，B 级改动涉及纯计算的分支、边界值或集合语义，且现有测试没有覆盖时，写临时表驱动测试：先在原实现上跑通，改写后重跑。临时测试集中放在被测包的 `zz_simplify_tmp_test.go`，最终验证后删除，报告写明它们验证了什么；用户要求保留时改名为正式测试文件。

## 缺陷扫描

缺陷扫描与简化同等重要。读每个函数时逐项检查，命中的写进报告「发现」，代码保持原样：

- **锁**：
  - 没有配 `defer` 的 `Lock()`/`RLock()`，检查它到 `Unlock()`/`RUnlock()` 之间每条 `return`、`continue`、`break` 和可能 panic 的路径，确认都会解锁。
  - 在 `RLock` 下写 map、字段或通过指针修改共享对象。
  - 同一个 map 或字段在不同函数里由不同的锁保护，或有的地方不加锁读写。
  - 持有 `RLock` 时再申请同一把锁的 `Lock`（读锁升级会死锁），包括经由被调函数间接申请。
  - 持锁期间做数据库、RPC、消息推送等 I/O（一般级别）。
- **错误**：
  - 错误分支只记日志就返回，但返回值仍表示成功（error 为 nil、错误码对象为 nil），调用方会按成功处理。
  - `err` 被赋值后没有检查就被覆盖。
  - `:=` 遮蔽了外层随后还要读的变量。
- **格式串**：项目自定义的 `Xxxf` 日志或错误函数，格式符的数量和类型与参数一致。`go vet` 识别不了大多数自定义包装函数。
- **敏感信息**：代码和测试里硬编码的密码、token、DSN、公网 IP。
- **注释**：注释描述的行为与代码相反或已过时。
- **其他**：向可能为 nil 的 map 写入、未检查长度的下标访问、循环里的 `defer`、没有退出条件的 goroutine。

每条发现标注严重程度：**严重**（死锁、数据竞争、金额或状态错误、安全问题）、**一般**（错误被吞、日志错误、边界缺陷）、**轻微**（拼写、过时注释）。改动前就存在的缺陷另标「原有」，提示用户单独修复。

## 简化清单

按收益从高到低排列，具体写法与反例见 [patterns.md](references/patterns.md)。

1. **控制流**：函数体内 `if`/`for`/`switch`/`select` 的嵌套不超过 3 层，单个分支或循环体不超过约 20 行。超出时依次使用：
   1. 错误、边界和不需要处理的情况先 `return`/`continue`；两个分支一长一短时，先处理短的再跳出。
   2. `return`/`continue`/`break` 之后去掉 `else`；`if ok { 长 } else { 短 }` 改为 `if !ok { 短; continue }` 后接长分支。
   3. 同一变量的三个以上比较分支改 `switch`。
   4. 仍然超出时，把职责独立的分支或循环体提取为方法（B 级，前提见 traps.md「控制流」：锁、`defer`、`return`/`continue` 的去向）。

   拉平跨越加锁区域时，`Lock` 与 `Unlock` 的配对和覆盖的语句保持不变（见 traps.md「并发」）。
2. **冗余**：未使用的赋值、永远为真或为假的条件、注释掉的代码、`len` 之前多余的 nil 判断、`delete` 之前多余的存在判断、只转发一次且名字没有提供额外信息的中间变量、首次读取前就被覆盖的初始化。
3. **重复**：输入、副作用、执行顺序都相同的重复代码块，提取为名字能说明职责的函数（B 级）。长函数里的重复块同样处理，不因函数长、改动大就整体放弃；只是长得像的代码见「克制」。
4. **作用域**：变量声明移到首次使用处；只在一个分支或循环里用到的变量，声明移进该块；只在 `if`/`switch` 内使用的值放进初始化语句；缩短贯穿整个函数的临时状态。
5. **错误处理**：保留已有的错误包装语义，`%v`、`%w`、`errors.New` 和错误文本都不改；`if err != nil { return err }; return nil` 合并为 `return err`（`err` 的静态类型为 `error` 时）。
6. **返回值**：
   - 命名结果加裸 `return`：函数有多个返回点或较长时，改为显式返回；短函数可以保留。同类型的多个结果靠名字说明含义时（如 `(lo, hi int)`），保留结果名，只把裸 `return` 改成显式。`defer`/`recover` 读写结果时保持原样。
   - 结果始终为同一个值，或所有调用方都忽略某个结果：删除它属于改签名。函数未导出、所有调用点都在范围内一起修改、没有用于满足接口或作为函数值传递时为 B 级，否则为 C 级。
7. **标准库写法**，以文件生效的 Go 版本为准：

   | 版本 | 可用写法 |
   |------|----------|
   | 1.18+ | `any`、`strings.Cut`、`bytes.Cut` |
   | 1.21+ | `min`、`max`、`clear`、`slices`、`maps` |
   | 1.22+ | `for i := range n`、去掉循环变量副本 `v := v`、`cmp.Or` |

8. **命名**：目标是看名字就知道它装的是什么、用来做什么。只改局部变量、参数、结果名和未导出标识符；导出名（包括与包名重复的 `user.UserInfo`）和协议、表结构字段的改名列为 C 级建议。示例见 patterns.md「命名」。
   - **说清内容和职责**：替换 `data`、`info`、`tmp`、`res`、`ret`、`obj`、`flag`、`_x`、`x2` 这类没有信息量的名字，以及与实际内容不符的名字（存剩余步数的 `totalSteps` 改为 `remainingSteps`）。
   - **长短与作用域相称**：几行内用完的循环变量、range 值、短闭包参数用短名；跨越几十行或多个分支的变量用完整的名字。惯用短名保持原样：`i`/`j`/`k`、`n`、`err`、`ctx`、`ok`、map 遍历的 `k`/`v`、测试里的 `t`/`b`/`tc`/`got`/`want`、`mu`、`wg`、`buf`、`req`/`resp`。
   - **MixedCaps 与缩写**：`betmoney`、`user_id` 写成 `betMoney`、`userID`。缩写整体保持同一大小写：`ID`、`URL`、`HTTP`、`JSON`、`API`、`RPC`、`DB`、`IP`、`UID`；`userId` 写成 `userID`，未导出名以缩写开头时全小写（`id`、`url`）。
   - **不带类型、不重复上下文**：`playerList`、`nameStr`、`roomMap` 去掉类型后缀，同一作用域里同时有两种表示时保留后缀区分（`idStr` 与 `id`）；在 `Room` 的方法里，`roomID` 写成 `id` 仍然清楚时去掉前缀。
   - **集合**：切片用复数（`players`）；map 的名字说明键（`playerByUID`、`roomsByAgent`）。
   - **布尔值**：读起来是判断（`ok`、`found`、`isAI`、`hasBet`、`canJoin`）；并列的 `ok1`、`ok2` 改成各自的含义（`hasSession`、`hasBet`）。只改名，逻辑保持原样。
   - **单位**：类型没有表达单位的数值带上单位（`delayMs`、`startSec`、`tsMilli`），毫秒和秒混用的代码尤其需要。
   - **一个概念一个名字**：同一个函数里，同一个用户 ID 统一叫一个名字，而不是 `uid`、`userId`、`playerid` 混用。
   - **返回值**：命名结果和保存最终返回值的局部变量按内容命名（`settings`、`allBet`），替换 `ret`、`res`、`result`、`data`。
   - **遮蔽**：局部名避开内置名（`min`、`max`、`len`、`new`、`copy`、`cap`）和函数里用到的包名（`log`、`time`、`url`）。参数已经遮蔽内置名时改参数名（见 traps.md「命名」）。
   - **receiver**：同一类型的 receiver 名一致；项目统一使用的写法（如 `this`）视为项目约定，保持原样。
   - **拼写**：修正局部名的拼写错误（`lcation`、`agrs`）；导出名、协议字段和用户可见文本里的拼写错误列入「发现」。
9. **注释**：删除复述代码的注释；保留解释原因、约束、契约、`//go:`/`//nolint` 等指令的注释；修正后的 doc comment 以标识符名开头。条件取反、分支重排后，同步更新挂在上面的注释。与代码矛盾的注释，已从代码查证本意的直接修正（A 级），无法确定的列入「发现」。

## 克制

简化追求的是可读性，不是行数。反例见 patterns.md「反例」。

- 一行做一件事。需要嵌套闭包、长链式调用才能变短的代码保持多行。
- 泛型、interface、helper、option 模式只在多个调用点都受益时引入。
- 只合并输入、失败处理和调用顺序都相同的代码。
- 提取函数时要能起一个说清职责的名字；起不出来就留在原函数里。
- 风格统一类改写（`interface{}` → `any`、receiver 改名）只在本来就要改的函数里做，用户明确要求时例外；import 分组和 gofmt 按第 6 步处理。
- 错误分支以显式 `return` 结束，即使它后面紧跟函数末尾的 `return`：否则以后追加在末尾的代码会在出错时执行。
- 同一文件的返回风格保持一致（命名结果加裸 `return`，或显式返回）：范围是整个文件或目录时同类函数一起改，否则沿用文件原有风格。
- 发现的缺陷只报告。修复会改变行为，由用户决定。

## 验证

在 scope.go 输出的 module 目录下运行，`<pkgs>` 和 `<files>` 取自脚本输出：

```bash
gofmt -l <files>
go build <pkgs>        # 有删除或移动文件时为 ./...
go vet <pkgs>          # 同上
go test -skip '<外部依赖测试>' <pkgs>
go test -race -skip '<外部依赖测试>' <pkgs>   # 改动涉及 goroutine、锁或 channel 时；需要 cgo
```

- 项目配置了 golangci-lint 或 staticcheck 时一并运行。缺少的工具不安装，报告中注明。
- 没有外部依赖测试时省略 `-skip`；`-skip` 需要 Go 1.20+ 工具链，更早的工具链改用 `-run` 只列出要运行的测试。
- `-race` 在 Windows 上可能因缺少 gcc 或 ThreadSanitizer 初始化失败而无法完成，此时记为未运行，不能记为通过。
- Windows 下 CRLF 文件会被 `gofmt -l` 全部列出，用 `gofmt -d` 确认差异是否只有换行符。

## 报告模板

```markdown
## 简化结果

范围：<N 个文件，涉及 M 个包>；模式：<快速/深度>

### 发现（未修改，按严重程度排序）
- [严重][原有] `<文件>:<行号>` `<函数>`：<缺陷描述>。影响：<会导致什么>。修复方向：<一句话>

### 改动
- A 级：<类别及数量，如"拉平嵌套 6 处、收紧作用域 9 处、局部改名 12 处">；主要位置：<函数列表>
- [B] `<文件>` `<函数>`：<改了什么>。等价依据：<查证了什么>

### 建议（C 级，未实施）
- `<位置>`：<建议>。未实施原因：<触碰哪条红线或缺少什么前提>

### 测试覆盖（仅深度模式）
- `<函数>`：<临时测试验证了什么>；未验证：<没有被测试断言的部分>

### 验证
- go build / go vet / go test：基线 <结果> → 结束 <结果>
- 排除的测试：<测试名及原因>
- 未运行：<检查项及原因>
```

有严重级别的发现时，在报告第一行用一句话提示。没有可做的改动时直接说明零改动，并照常列出发现与建议。未运行的检查不能写成通过。
