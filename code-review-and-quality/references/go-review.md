# Go 代码审核

用于 Go 变更的专项核对。只读取与当前变更有关的部分；按目标项目的规则和业务契约判断，不把模式清单直接当作缺陷。审核保持只读，不依赖其他技能。

## 构建与审核基线

- 确认文件所属 go.mod、项目支持的 Go 版本、toolchain、GOOS/GOARCH、build tags、CGO 和现有 go.work。当前终端版本不代表所有部署目标都支持同一 API；独立 module 分别核对，不临时添加 replace/go.work 串联。
- 当前改动包含相关暂存、未暂存和未跟踪文件；指定提交则固定 base/head。读取完整函数、测试和必要调用方，区分本次引入、基线已有及无法确认的问题。
- 按生成文件头和生成流程识别产物。协议、配置生成物的改动要检查源和生成器，不能只建议直接修正生成文件。
- 符号身份、接口实现和方法集优先用可用的 gopls/LSP 或已有语义工具核对。补查反射、序列化、注册、生成输入及当前构建之外的消费者；仓内无引用不能证明公开 API 可删除。

## 类型、控制流与错误

| 检查点 | 需要确认的行为 |
| --- | --- |
| nil 与空值 | nil interface 与装有 typed nil 的 interface 是否被混淆；nil slice/map、空集合、缺失键和零值是否有不同协议含义？ |
| 数据共享 | slice 的底层数组、长度/容量，map/pointer 的别名，以及对象池借还是否保持所有权？复制结构是否复制了同步原语或资源 owner？ |
| 求值与分支 | guard、布尔简化、switch、提取或内联是否改变短路、调用次数、随机/时间读取、循环尾部及副作用顺序？ |
| 错误与部分结果 | sentinel identity、errors.Is/As、错误链、首个错误和部分成功是否保持；新增包装或忽略错误是否改变调用方决策？ |
| 返回与 defer | 直返是否省去了 defer 依赖的局部赋值；命名结果是否参与恢复或收尾；参数是在登记 defer 时还是闭包执行时读取？ |
| 接收者与接口 | 值/指针接收者、方法集、嵌入和类型别名变化是否影响实现、复制语义或外部调用方？ |

错误遮蔽、channel 未关闭、goroutine 没有 Context 等模式本身不是缺陷。追到错误是否已返回、有限工作能否完成、接收者是否依赖关闭等实际契约。没有必要的调用链证据时，报告待核验条件。

对于金额、概率或随机相关代码，核对单位、舍入、溢出、随机调用次数与顺序。不能因类型检查或普通回归通过，就推断收益分布未变化；统计验证只在改动影响分布且项目要求时执行。

## 状态、并发与生命周期

- 找到可变状态的权威来源、修改者、同步保护和发布时点；初始化完成前是否可能被读取，缓存是否重复持有无独立语义的业务状态？
- 沿创建、部分初始化失败、启动、正常执行、取消和关闭逐条追踪。核对失败回滚及关闭顺序，资源不能在使用者退出前关闭。
- 每个 goroutine 要有可说明的结束方式和必要的等待位置。有限工作可以自然结束；阻塞的收发、锁和 I/O 需要与协议一致的退出路径。WaitGroup 负责等待，不负责取消。
- channel 的发送与关闭要有明确 owner 和顺序依据。sync.Once 只能避免重复执行，不能证明发送已结束；存在多个可就绪 case 时不能假设 select 总先选择取消。
- 保持锁覆盖的不变量、锁顺序和锁内调用时序。把慢操作搬出锁、将 Mutex 换成 RWMutex/atomic，均需要契约和适用负载的依据。
- 区分准入前取消、业务已经接受后的收尾和外部效果可能已发生的阶段。不能把 Context 取消自动等同于业务回滚或资金失败。
- panic/recover 是否是明确的隔离边界，是否能报告失败并保持状态一致？不能给所有 goroutine 统一加 recover 来掩盖故障契约。

## 数据库、缓存和外部效果

- 检查事务内的查询和写入是否使用同一个事务/连接 owner；连接池、行锁、命名锁及 rollback/commit 错误是否沿真实调用路径处理。
- 对 SQL/RPC/HTTP/消息投递区分成功、明确失败和结果未知。超时或响应丢失不证明效果未发生；重试是否保留原操作 ID、参数摘要和恢复证据？
- 区分本地入队、transport 接收、broker ACK、消费者处理和最终落库。返回值与日志不能把某个中间阶段误称为最终成功。
- 对幂等、租约和 TTL 检查原子认领、并发请求、迟到结果及最长补投路径；不能通过重建 ID、清空状态或重复执行来消除未知状态。
- 鉴权检查资源 owner 与租户边界，不能仅验证登录或信任请求里的用户/商户编号。缓存键和查询过滤必须对应实际权限范围；错误与日志不能泄漏凭据或完整敏感 payload。
- 数据库和 Redis 等动态标识符、表名、排序项需明确白名单；值使用参数。已有静态内部值和外部输入应分别判断，不机械报告所有字符串拼接。

## 测试与验证证据

先检查 TestMain、包初始化、环境变量、fixture 和清理行为，确认不会连接真实业务资源。优先使用项目入口与已有隔离资源；以下包名必须替换为实际受影响范围：

```sh
go test ./path/to/package
go vet ./path/to/package
# 并发访问、同步或退出协作变化时，按项目规则验证相关路径。
go test -race ./path/to/concurrent/package
```

- 测试应实际执行受影响的失败与边界路径，不只验证编译。跨平台编译、跳过的集成用例或历史结果不能报告为本次执行通过。
- 核对所选 Go 命令是否会补写依赖文件；需要下载或补全 go.mod/go.sum 的验证使用隔离副本或报告缺口，不在受审树原地生成、tidy 后再还原来冒充只读。
- 并发测试关注可控同步、终止等待和有界超时。固定 sleep、goroutine 瞬时数量和一次 race 通过都不能单独证明退出或并发正确。
- 新测试针对可观察风险；纯命名、格式和已证明等价的直返不要求新增套件。不能为测试方便扩大公开接口或增加生产全局开关。
- 性能结论应有同条件 benchmark/profile/监控或明确复杂度依据。说明测量范围和局限，避免把微基准推断为完整业务吞吐。
- 审核报告区分亲自执行的验证、作者提供的证据和未验证区域；遵循项目独立复核要求，不用自审冒充独立复核。

语言与模块行为以目标版本的 [Go 规范](https://go.dev/ref/spec) 和 [Go Modules Reference](https://go.dev/ref/mod) 为准；依赖包按本地解析版本查证。
